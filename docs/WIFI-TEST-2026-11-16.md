# TYC4A RTL8822CS Wi-Fi and SSH test, 2026-11-16

This adds SDIO Wi-Fi to the working eDP/USB console configuration. The original
Android source names RTL8822CS; the running device reports SDIO vendor 024c,
device c822, using rtl88x2cs. Linux 6.18.63 has the matching rtw88_8822cs driver.
The initial build uses a separate 6.18.63-tyc4a-wifi01 release and preserves the
working 6.18.63-tyc4a-edp01 kernel and edp03-usb DTB as a fallback.

The SDIO controller is fe2c0000, four bits, capped at 50 MHz without UHS voltage
switching. Reset is GPIO2_B1 active low with a 200 ms post-power delay and RK809
clock output 1. The stock always-on Wi-Fi enable rail uses GPIO1_A0 active high;
its unknown voltage constraints are intentionally not invented. SDIO IO-domain
supply remains 1.8 V as in the original board source. Internal eMMC remains
disabled. Bluetooth and suspend are outside this initial test.

Run the `TYC4A RTL8822CS Wi-Fi kernel` Actions workflow, or on native ARM64 Linux:

```sh
export TYC4A_BUILD_WORK=/absolute/dedicated/build-directory
# Download the checksum-pinned archive listed in kernel.env into this directory.
bash experimental/wifi/build.sh
```

The build verifies the ARM64 Image, module archive, SDIO GPIO and clock wiring,
and the existing screen clock, display graph and USB keyboard mapping. These
checks do not establish a successful Wi-Fi hardware test.

The local SD setup installs Debian openssh-server, wpasupplicant,
wireless-regdb and firmware-realtek. Firmware path is rtw88/rtw8822c_fw.bin.
An interface-specific supplicant and systemd-networkd DHCP configuration are
prepared separately on the user's card. SSH permits only the tyc4a account,
with a dedicated Mac key; root and SSH password authentication are disabled.
The local console password remains independent. No Wi-Fi credentials, private
keys, account passwords or ready-to-login images are included in this repository.

## Initial hardware result

The new kernel booted from the local SD card. Its rtw88_8822cs driver matched
SDIO 024c:c822, loaded firmware 9.9.15 (H2C 15), and negotiated a 50 MHz,
four-bit SDIO bus. The interface was renamed to tycwifi0, completed a 5 GHz
WPA2-PSK association, and acquired DHCP IPv4 and IPv6 addresses. A Mac logged in
as tyc4a with its separately configured private key. A subsequent session
verified sudo authentication with the locally configured console password and
successful DNS resolution. VPLL and VP1 pixel clocks remained 594 MHz and
148.5 MHz.

The initial connection dropped and automatically reconnected. Initial runtime
follow-up disables rtw88 deep power saving and normal Wi-Fi power saving.
Debian's default regulatory.db alternative is signed by Debian's key, which
this kernel does not trust. The selected alternative is instead the package's
upstream-signed regulatory.db plus its matching signature, retaining kernel
signature verification. A subsequent warm reboot again reached the text console and briefly accepted
an SSH connection, but repeated packet loss and connection timeouts remain.
The warm-boot diagnostics subsequently confirmed that normal power saving was
off, deep power saving was disabled, and the persistent service succeeded.
Disconnects therefore persisted despite those settings taking effect.

A reversible compatibility test adds `disable_vht=1` and `disable_ht40=1` to the
private network profile. The running interface confirms a 20 MHz channel.
Four SSH command samples all succeeded, and a 256 KiB SSH download passed an
exact content check in 4.12 seconds. However, a subsequent 120-packet ping test
received only 94 replies (21.7% loss), with signal approximately -75 to -81 dBm.
These observations do not establish that the width change fixed the problem.
The original network profile is backed up locally on the card. The control
fields are documented in the [supplicant source](https://android.googlesource.com/platform/external/wpa_supplicant_8/+/master/wpa_supplicant/config_ssid.h).

A further warm reboot with the compatibility profile automatically associated
with the selected network and restored keyed SSH access within the bounded
observation (73 seconds). A changed boot ID confirms this was a new boot.
Remote checks verified the same kernel release, a DHCP address, active SSH and
supplicant services, both power-saving settings disabled, and a 20 MHz channel.
The signal remained approximately -80 dBm. A closer-range physical test is
requested to distinguish weak reception from driver compatibility. Wi-Fi is
not yet considered stable. Long-term performance, roaming, suspend and battery
life are not validated.
