# TYC4A diagnostic SD boot test, 2026-11-16

One TYC4A RK3566 board booted the diagnostic SD configuration to Debian trixie ARM64 multi-user state.
The evidence was written by the SD oneshot service during Linux execution and retrieved later from Android.
No internal Android block device was written.

Evidence from the matching boot ID:

```text
Linux tyc4a 6.18.63-tyc4a-v07 ... aarch64 GNU/Linux
Machine model: TYC4A RK3566 SD boot diagnostics
root=PARTUUID=74c4a007-01 rootfstype=ext4 rootwait rw ...
/dev/root / ext4 rw,noatime 0 0
[9.262994] Reached target multi-user.target - Multi-User System.
[9.278337] Startup finished in 1.112s (kernel) + 8.165s (userspace) = 9.278s.
[87.817757] Power key pressed short.
[87.825809] System is powering down.
[89.200098] Syncing filesystems and block devices.
```

The LED trigger file reports `[heartbeat]`. Visible flashing was not confirmed by the operator.
The SD rootfs and userspace run; this does not establish a usable display, network, keyboard, unlocked account, or long-term stability.
Board/guest calendar clocks are not synchronized. Durations above use monotonic time.
The tested card contains the additional diagnostic DTB and rootfs service; the original cloud image is unchanged.

The black display has a concrete kernel error:

```text
rockchip-drm display-subsystem: No available vop found for display-subsystem.
```

Android reports a connected eDP panel and disconnected HDMI. The pinned 6.18.63 source lacks
`rockchip,rk3568-edp` in the Rockchip Analogix driver and lacks the Naneng eDP PHY driver.
Enabling the internal screen requires driver backports as well as board DT integration.
The original panel uses fixed 1920x1080 timings; its Android EDID sysfs read returns zero bytes.
Keep the boot-tested diagnostic configuration as a fallback during display development.

Upstream starting points:

- [RK3568 eDP PHY and DTS v6 series](https://lkml.rescloud.iu.edu/hypermail/linux/kernel/2611.1/21492.html)
- [Bridge/display patches accepted into drm-misc-next](https://lists.openwall.net/linux-kernel/2026/11/03/2828)

Those patches target a newer development tree and a different board/panel. They are not proof of TYC4A display operation.
